# Архитектура

Документ описывает код текущей ветки. Инструкция игроку находится в [описании пакета](../package/README.md), команды разработчика — в [руководстве по сборке](BUILD.md).

## Сборка и стандартные зависимости

`Tolmach.csproj` включает `src/**/*.cs`. Ссылки на библиотеки выбранного профиля задаёт `build/RuntimeReferences.props`. Тестовый проект использует production DLL через `ProjectReference`, а не повторно компилирует выбранную часть исходников. NUnit управляет тестами, VSTest пишет TRX. `Build.ps1` запускает тесты, передаёт проверенные файлы Thunderstore CLI и проверяет готовый ZIP. Установку выполняет менеджер модов; собственного установщика нет.

Json.NET разбирает каталоги. Harmony выполняет поиск членов по иерархии, чтение инструкций и установку патчей. `RuntimeAccess` оставляет только политику точного выбора типа, получателя и имени метода для диагностики. Собственного JSON-декодера, IL-декодера или универсального пути рефлексии нет.

## Каталоги и привязка модов

`CatalogLoader` сопоставляет GUID, имя сборки и `pluginVersion`; версия пакета хранится отдельно. Отсутствующие нулевые компоненты версии нормализуются, ненулевой revision учитывается. Неуспешная повторная привязка очищает прежний runtime-контекст.

В Conditional Config Sync GUID принадлежит сборке плагина, а окно ошибки обслуживается отдельной DLL. Необязательное `codeAssembly` выбирает её только для адресных IL-адаптеров: сборка должна быть прямой зависимостью привязанного плагина и единственной уже загруженной сборкой с точной идентичностью ссылки. Tolmach не загружает DLL и не ищет произвольные сборки по пространству имён. При отсутствии или неоднозначности помощника UI-адаптеры пропускаются с предупреждением; проверка GUID и версии остаётся у плагина. Нативные словари используют исходную сборку плагина. Так существующие адаптеры можно применить к отдельной DLL без общего перехвата текста игры.

Типы в `Models.cs` запрещают неизвестные члены и `null` вместо таблиц. Дополнительная проверка контролирует непустую идентичность и плейсхолдеры. Та же форма описана в [JSON Schema](../tools/catalog.schema.json), которую использует `validate.py`. Грамматика шаблонов CLLC проверяется согласованно схемой и загрузчиком; это защищено тестом.

Плагин читает только `tolmach-<id>.json`. Префикс необходим: встроенный в другие моды LocalizationManager может принять файл `<имя плагина>.*` за свой перевод. Типы без пространства имён обозначаются в каталоге как `<global>`, не пустой строкой.

Конфликтующие общие ключи и сырые строки отклоняются валидатором до выпуска. Runtime также предупреждает о конфликтах; порядок модулей для сырых строк фиксирован по `id`. При этом таблица каждого владельца сохраняет собственный словарь для явно объявленных аргументов его шаблонов.

Модуль игры использует зарезервированный GUID `valheim`, сборку `assembly_valheim` и `Version.CurrentVersion`. Записи BepInEx у самой игры нет. Словарному модулю не требуются пространства имён для сканирования IL.

По умолчанию адресные адаптеры пробуют известные строки на другой версии мода. `OnlyAuditedVersions = true` оставляет для отличающейся версии только нативные ключи. Совпадение строки не является подтверждением совместимости всего экрана. Предупреждения описывают известные отсутствующие цели, а не все новые фразы мода.

## Нативные словари

Jötunn владеет своими `CustomLocalization`. Адаптер использует публичные `GetTranslations` и `AddTranslation`, учитывая `in string` в сигнатурах 2.30.2. Русские строки регистрируются только при выбранном русском языке: `AddTranslation` может сразу добавить отсутствующий ключ в активную игровую таблицу, даже если переданный язык не выбран. Доступ к внутреннему реестру нужен только для получения scope другого мода: публичный `GetLocalization` не является универсальным поиском чужого scope. Внутренняя `Map` не читается.

Встроенные `LocalizeKey`-менеджеры получают перевод через свой Russian API. При отсутствии setter адаптер предупреждает, а не пишет напрямую в их внутренний словарь. Fill-only защита регистрируется до setter, поскольку тот может немедленно вызвать игровую регистрацию.

Игровые ключи читаются через `Translate` и добавляются через `AddWord`. Отсутствующее или английское значение дополняется, существующий русский текст сохраняется, в том числе при повторной регистрации модом. Исключение — явно перечисленные `replaceNative`, описанные в [покрытии](COVERAGE.md#исключения-и-ограничения). Они имеют приоритет и в Jötunn, и в основной игровой таблице.

Заполняется только основной `Localization.m_instance`. Дополнительный английский экземпляр, созданный сторонним менеджером для ключей конфига, не становится русским.

Кеш локализации (LocalizationCache) отдаёт каждому новому экземпляру тот же словарь, что у основного. Тогда английские слова, которые мод записывает в свой отдельный экземпляр, попали бы в текст игрока: и перевод Tolmach, и собственный русский игры. Поэтому `AddWord` экземпляра, чей `m_translations` совпадает по ссылке с основным, не меняет уже заполненный ключ. Отсутствующий ключ добавляется и проходит те же правила, что запись в основной экземпляр. Словарь только сравнивается по ссылке, не читается и не меняется. Язык основного экземпляра берётся из `GetSelectedLanguage`; PlayerPrefs — запасной путь. Пока экземпляр строится, первое заполнение может быть отложено до `Refresh` из меню, `Start` или события локализации Jötunn.

После регистрации сбрасывается игровой кэш через его `EvictAll`. Получение `m_cache` остаётся частной точкой интеграции, как и получение чужого scope Jötunn; наличие этих членов проверяется, но их доступность в будущей игре не гарантируется.

## Таблицы текста и составные сообщения

`TextTable` выполняет точное сопоставление и ограниченные шаблоны стандартного Regex с тайм-аутом. Аргументы по умолчанию непрозрачны. Перевод разрешается явно: `text`, `mapLabel`, вложенный `message`, закрытый словарь `term:<имя>`, а для адресных шаблонов — `item` и `itemSet`. Вложенность сообщений ограничена; неизвестная часть закрытого словаря оставляет составное название исходным.

Для причин отказа Conditional Config Sync шаблоны помечаются `singleLine`: аргумент не может захватить соседнюю строку LF/CRLF. Несколько причин переводятся независимо. Шаблоны без флага сохраняют прежнее сопоставление. Перевод выполняется при выводе сообщения; сетевые причины, управляющие проверки синхронизации и журналы остаются исходными.

Имя мода может само содержать двоеточие и начало известной фразы ошибки, поэтому разбирать готовую строку `имя: причина` шаблоном недостаточно. `CcsDisplay` читает результат `NormalizeDisconnectReasons` без изменения полей. Он хранит ограниченный набор исходных строк вместе с отдельно полученными именем и причиной, привязанный к конкретному ожидающему отчёту CCS. При выводе переводится только причина, а имя добавляется дословно. Замена или сброс отчёта исключает использование старой структуры; переинициализация очищает состояние. Перехватываются методы проверенной вспомогательной DLL, а не общий вывод игры. Старое сообщение без структурированных данных получает перевод известных заголовков; неизвестная граница имени и причины остаётся исходной.

Динамические значения самой причины также могут содержать разделитель шаблона. Только таблица CCS сравнивает захваты ленивого и жадного сопоставления; разные результаты оставляют причину исходной. Это относится и к соседним имени и версии, разделённым одним пробелом. Обычные таблицы сохраняют прежнее поведение.

`GameItems` читает ObjectDB, чтобы Recipe Description Expansion показывал игровые названия частей и комплектов, а не внутренние имена. Для комплекта учитывается регистр ключа; при отсутствии объекта возвращается исходный текст. ObjectDB не изменяется. `item` и `itemSet` не разрешены в глобальных сырых шаблонах.

`TranslateWhole` обрабатывает одну исходную строку, не разбивая её. Общая операция `TranslateRaw(value, translateWhole)` сначала пробует сообщение целиком, затем разбивает исходный текст на строки и фрагменты между тегами Unity. В каждый вызов передаётся **исходный фрагмент**, никогда результат предыдущего перевода. Теги, переносы и внешние пробелы сохраняются.

`RawDisplay` выбирает подходящий каталог отдельно для каждого такого фрагмента. Поэтому одна подсказка может использовать разные каталоги, а `A → B` одного модуля не запускает `B → В` другого. Сначала проверяются целые сообщения всех владельцев, затем частичные фрагменты. Словари аргументов остаются привязаны к владельцу шаблона.

Кэш обычной таблицы ограничен 1024 изменёнными результатами. Общий кэш `RawDisplay` ограничен 4096 попаданиями и промахами; сбрасывается при переинициализации. Это не основание считать путь быстрым без профилирования: промах может проверить несколько каталогов и шаблонов.

## Глобальные сырые строки и имена существ

`LocalizationBridge` применяет `RawDisplay` до разрешения игровых `$`-токенов, только для основного экземпляра и русского языка. Используются модули с разрешёнными UI-адаптерами. Это путь для названий, описаний, эффектов и записей справочника, переданных без словарного ключа; прежние записи `prefabs` включаются в тот же набор.

Составные названия идолов Valheim описаны отдельным необязательным `nameAliases`. Загрузчик и валидатор разрешают только 16 проверенных комбинаций `$item_upgrader_tier[0-7] $item_upgrader_(weapon|armor) $item_upgrader_name` в каталоге игры. Каждая комбинация ссылается на соответствующий собственный ключ `$tolmach_idol_<уровень>_<тип>` с полным русским и английским названием. Значения не могут содержать токены, теги или аргументы; исходные ключи игры не переопределяются. При инициализации `RawDisplay` ссылки превращаются в точные пары «исходная строка — полное русское имя» и используют существующий ограниченный кэш. Проверка сохранения токенов в обычных `rawTexts` остается обязательной. Такой контракт исправляет порядок слов без универсальной обработки падежей и без изменения имени в объекте или сохранении.

**Ограничение происхождения:** глобальная точная строка не содержит сведений об авторе. Пользовательский текст, совпавший с каталогом, может отображаться переведённым. Сохранённое поле не меняется. Не следует описывать этот механизм как полную защиту любого пользовательского имени.

Широкие `rawPatterns` Humanoid Randomizer исключены из `RawDisplay`. Их обслуживает `CreatureNameDisplay`:

1. Проверяется модуль HumanoidRandomizer и его разрешение на UI-адаптеры. `CreatureNameOwner` распознаёт исходные объекты по компоненту `BalrondHumanoidRandomizer.HumanoidRandomizer` из привязанной сборки.
2. С созданных вариантов мод удаляет этот компонент. Для них читается ID префаба из `Character.m_nview.GetZDO().GetPrefab()`: объект, возвращённый `ZNetScene.instance.GetPrefab(id)`, должен находиться в текущем `Launch.itemSetBuilder.prefabs` мода. Сравниваются сами объекты, а не их имена. Принадлежность не кешируется: мод пересоздаёт список при загрузке сцены.
3. В `Character.GetHoverName` перевод вставляется после безопасного чтения `this.m_name`, а в `Tameable.GetName` — после `this.m_character.m_name`, до игровой локализации. `Character.GetHoverText` делегирует показ в `Tameable`, поэтому отдельного патча не требует. Ветви пользовательского имени и ZDO-переопределения не подменяются.
4. Перед заменой исключаются игроки. Используется исходное имя существа; `m_name`, имя прирученного существа и ZDO не записываются. Отсутствующий API, неподходящий IL или ошибка проверки происхождения оставляют оригинал и дают предупреждение. Глобального запасного применения шаблонов нет.

Транспайлер сохраняет исходные инструкции и не вставляет вызов на непроверенной границе исключения или входящей метке. Фактически найденные чтения отражаются в `PatchEvidence`. NUnit проверяет этот контракт на средовых типах; реальные методы игры и сочетания патчей требуют отдельной приёмки.

### Имена NPC Norsemen

`NorsemenNames` использует закрытый словарь `terms.npcNames` модуля Norsemen. Вызовы `GetName` и `GetText` подменяются только в местах отображения: подсказках `Viking` и окнах `VikingGui`. Исходные методы, ZDO и файл `Names.yml` не изменяются; другие потребители имени, в том числе сохранение надгробия, получают исходное значение.

Перевод разрешён только для неприручённого `Norsemen.Viking`, русского языка и активного UI-модуля. Генерация стандартного имени и переименование игроком используют одно поле `s_tamedName`; после приручения их происхождение неразличимо, поэтому имя сохраняется, даже если совпадает с известным стандартным именем. Неизвестное имя или недоступный API также оставляют исходный текст. `terms.npcNames` не участвует в глобальном `RawDisplay`.

### Составные подсказки хранилищ

`Container.GetHoverText` может сначала объединить исходное имя с суффиксом пустого хранилища и только затем вызвать локализацию. Точное правило для имени в таком случае не совпадает со всей строкой. `ContainerNameDisplay` переводит чтение `m_name` внутри `GetHoverText` и `GetHoverName` до этой композиции. Используются только точные `rawTexts` активных каталогов Dynamic Storage; произвольная замена подстроки не выполняется. Поле контейнера и сохранённые данные не меняются.

## Адресные IL-адаптеры

`DisplayPatches` выбирает известные методы и поля показа только в разрешённых пространствах имён загруженного мода. Словарные модули не сканируются. Модуль только с литералами не получает общий перехват UI. Правила литералов могут охватывать конструкторы экземпляров; при перегрузках выбирается тело, где исходный IL содержит нужную строку.

Раздел `configTexts` переводит чтение `ConfigEntry<string>.Value` в конкретном методе, только пока значение совпадает с английским по умолчанию. Примеры — Take All Cooked и два getter подписи слота Circlet Extended для ExtraSlots. Подпись AzuEPI одновременно служит идентификатором слота и не переводится. Пользовательский конфиг не меняется; замена литерала при записи значения по умолчанию была бы неверным местом применения.

Типы и методы с отсутствующими необязательными зависимостями пропускаются с предупреждением, не останавливая остальные адаптеры. Установка патча и подтверждение фактической замены различаются: при отложенной работе Harmony результат сообщает транспайлер.

### Методы с неподдерживаемыми обработчиками исключений

HarmonyX 2.9 из проверявшегося профиля не пересобирает часть методов с filter/fault корректно. `DisplayPatches` оставляет такие тела нетронутыми, поскольку StartupAccelerator может применить патч позднее, за пределами локального `try/catch` установки.

`CallSites` может переводить аргумент вызываемого метода показа (`GUI.Window`, `Character.Message`, `Player.Message`, `MessageHud.ShowMessage`), проверяя прямого вызывающего по стеку. Тот же текст от другого источника не получает этот адресный перевод. Стек читается после проверки, что каталог вообще меняет текст.

Этот обход не распространяется на общий `Localize`, Jötunn `TryTranslate`, запись полей, литералы, чтение конфига или возвращаемое значение исходного метода. Непокрытые цели остаются в `leftAsIs`; запись отчёта содержит `notPatched`, `callSites` и причину. Работа стека и сочетание отложенных патчей проверяются в игре отдельно. Оптимизация этого пути начинается с измерений, не с замены механизма по предположению.

## Карта и другие постоянные элементы

`AddPin` и `DiscoverLocation` не считаются универсальными UI-приёмниками. `PersistentUi` меняет подпись виджета, не `PinData.m_name`, сохраняет чужой перевод, обновляет известные подписи при смене языка и очищает ссылки при смене сцены. Личное имя `Camp`, совпавшее со стандартным, может отображаться как «Лагерь»; параметр `TranslateStandardMapLabels` отключает эту подстановку. Горячая смена настроек не поддерживается.

`ExtraHooks` дополняет словари при появлении меню и переводит точное уведомление Ore Mines в `Chat.OnNewChatMessage`. Консольные ответы Portal Preview переводятся только у вызовов `Terminal.AddString(string)` из обработчика `FrozenPortals+<>c.<Initialize>b__49_0`; аргумент проходит таблицу этого владельца. Общий `Terminal.AddString` не становится приёмником перевода произвольной консоли.

## Creature Level and Loot Control

CLLC читает свою YAML-таблицу `LocalizationWrapper` при запуске. Tolmach загружается после него по мягкой зависимости и при русском языке подставляет таблицу `cllc`; уже русская таблица дополняется. Роды, шаблоны и формы слов берутся согласованным блоком, чтобы не смешивать несовместимые коды родов.

Названия `display` и описания `desc` настроек заполняются независимо, каждое относительно собственного английского значения. Существующая запись сохраняет переведённое поле; повторное применение не считает его новым заполнением. Плейсхолдеры сверяются с английской таблицей. Английская таблица не должна меняться через разделяемую запись.

Тексты `ConfigurationManagerAttributes` пересчитываются через функции самого CLLC; имена секций и ключей `.cfg` остаются прежними. Этот адаптер не требует Harmony. После смены языка нужен перезапуск; некоторые сетевые сообщения CLLC другие участники видят на языке отправителя.

## Жизненный цикл и диагностика

`Plugin.Awake` создаёт новый `RuntimeReport` с идентификатором сеанса и записывает `Initializing` **до** чтения конфига и каталогов. Ранние выходы записывают `Disabled` или `MissingCatalog`. Успешная инициализация даёт `Active`, исключение — `Failed`, штатная выгрузка — `Stopped`.

При ошибке отчёт записывается до очистки контекста, чтобы сохранить предупреждения. Обновления одного запуска сохраняют `Session` и `StartedUtc`; новый запуск получает новый идентификатор. В журнал пишется тот же идентификатор для сверки.

`Russian selected` описывает определённый язык. Совместимый флаг `Russian active` истинен только при состоянии `Active` и русском языке. Ни он, ни число подключённых модулей не подтверждают каждый экран: ниже сохраняются состояния и свидетельства адаптеров. Отчёт не является сканером всех непереведённых строк.

Плагин, отключённый в менеджере или не дошедший до `Awake`, не может обновить старый файл. Ошибка записи отчёта также не позволяет считать файл свежим. Поэтому инструкция требует сверять сеанс и журнал, а не доверять существованию `Tolmach.runtime.txt`.

## Границы проверки

Наличие правильных API и прохождение NUnit не подтверждают полную цепочку BepInEx всех модов в Unity/Mono. Тесты используют production DLL и управляемые средовые типы; динамическая идентичность сборки не равна загрузке реальной DLL мода.

[Игровая приёмка](RUNTIME-CHECKLIST.md) проверяет загрузку, другие переводы, сохранённые данные, языки, UI и производительность. [Решения о переиспользовании](REUSE-DECISIONS.md) объясняют границы сравнения с XUnity; новой зависимости на XUnity нет.
